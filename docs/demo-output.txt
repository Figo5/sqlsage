## 1. Nullable NOT IN subquery can invalidate anti-membership  `correctness` `critical` `high confidence`

```sql
c.customer_id NOT IN ( SELECT e.customer_id FROM shop.events e WHERE e.event_type = 'checkout' )
```

_in `events.customer_id`_

SQL NOT IN becomes UNKNOWN for every otherwise-unmatched outer row if this subquery emits even one NULL. Catalog statistics report 14.5% NULL overall (about 725,170 of 5,000,022 rows) for events.customer_id. Because the IR cannot prove that the subquery filters every NULL out, the returned population is not trustworthy.

> **Does not apply if:** NOT IN is safe only when the outer comparison value and every value produced by the subquery are both proven non-NULL; filtering NULL inside the subquery preserves semantics but may not produce the same plan as NOT EXISTS.

### Fix — Use NULL-safe NOT EXISTS anti-membership  `changes results` `priority 1`

The original NOT IN can become UNKNOWN for every otherwise-unmatched row after one NULL. Correlated NOT EXISTS tests actual equality and is not poisoned by unrelated NULL subquery outputs.

```sql
SELECT c.customer_id, c.email
FROM "shop"."customers" AS "c"
WHERE (NOT EXISTS (SELECT 1 FROM "shop"."events" AS "e" WHERE e.event_type = 'checkout' AND "e"."customer_id" = "c"."customer_id"));
```

> **Returns different rows:** This intentionally repairs the original wrong-result behavior when the subquery can emit NULL; it can return outer rows that NOT IN incorrectly suppresses. Review that corrected population as a correctness change. An attached correctness finding explains why changing the current rows is the repair; validate the repaired rows against business intent or an independent oracle.

> **Expected effect (upstream):** No comparable speedup is claimed because the result population intentionally changes. The optional partial index can support the corrected anti-join after semantics are fixed.

> **Required companion index:** `idx-events-btree-customer-id-where-event-type-checkout-and-customer-id-is-not-n-ec75bbca` is present in this change set. Deploy and verify the complete set; no component inherits a measured benefit on its own.

### Index (required dependency) — events (customer_id) WHERE event_type = 'checkout' AND "customer_id" IS NOT…  `required dependency` `id idx-events-btree-customer-id-where-event-type-checkout-and-customer-id-is-not-n-ec75bbca` `priority 1` `high confidence`

Predicted/unverified: this index does not repair or accelerate the current wrong NOT IN semantics. After the M6 NOT EXISTS correctness rewrite, it can provide a compact non-NULL anti-join input.

```sql
CREATE INDEX CONCURRENTLY idx_sqlsage_events_btree_customer_id_where_event_type_52972e20 ON "shop"."events" ("customer_id") WHERE event_type = 'checkout' AND "customer_id" IS NOT NULL;
```

> **Before you run it:** `CONCURRENTLY` cannot run inside a transaction block (no `BEGIN`, and many migration tools wrap statements by default). It performs two table scans, can wait on old transactions, and if it fails it leaves an `INVALID` index behind that you must `DROP INDEX` before retrying.

> **Why this column order:** Fixed subquery filters and NULL exclusion belong in the partial predicate; customer_id is the correlated anti-join equality key.

> **What it costs:** Size is unmeasured. A full definition can store up to one entry per row across about 5,000,022 catalog-estimated rows. The partial predicate limits entries to rows satisfying event_type = 'checkout' AND "customer_id" IS NOT NULL; its exact size is not measured. Eligible inserts and rows entering/leaving the partial predicate plus updates to customer_id require index maintenance. Validate this rewrite-coupled partial anti-join index against workload frequency before deployment.

> **Serves:** The M6 NOT EXISTS correlation on e.customer_id; e.event_type = 'checkout'

## What this query does

One row per qualifying `customer` row.

- **Start with `customers` (`c`)** — Begin with rows produced by the table `customers`, named `c` in this query.
- **Apply the exclusion test** — Build the values returned by the nested query, then keep an outer row only when comparison with every value is true. If the nested values contain NULL, a nonmatching row becomes unknown rather than true and is removed.
  - `c.customer_id NOT IN ( SELECT e.customer_id FROM shop.events e WHERE e.event_type = 'checkout' )`

- `customer_id` — The `customer_id` value from `customers`.
- `email` — The `email` value from `customers`.

> **No output order is promised:** Without an explicit final ordering, consumers must not rely on the order rows happen to be returned in.
